# Repository Analysis: DeepSeek Harness and TrueForge

Status: Phase 0 deliverable
Scope: this analysis is based on reading the source code, and the docs were checked against it. Paths are relative to each repository root. Claims that could not be checked in code are marked **[unverified]**.

---

## 0. Summary

Both repositories are TypeScript monorepos. **Neither has a Python agent runtime:**
- DeepSeek's `python/sdk` is a JSON-RPC client that launches the `dsh` binary.
- TrueForge's `python/trueforge_sdk` is an HTTP/SSE client generated by Fern from OpenAPI.

So we will not port Python code from either. We will take ideas from both.

The two projects answer different questions:

| | DeepSeek Harness (`dsh`) | TrueForge |
|---|---|---|
| Central idea | *Everything is a plugin.* A small set of service seams plus typed events. The loop itself is a replaceable plugin. | *A turn is a durable, resumable unit of execution.* An opinionated runtime with built-in context-engineering features. |
| Source of truth | An append-only **session event log**. Model history is *derived* from it. | A persisted **per-thread context**: an array of ids into an immutable message log, copied on write for each turn. |
| Extension model | Cordis DI, plus event dispatch modes (`emit` / `serial` / `waterfall`), plus per-agent scopes. | `AgentCapability` bundles of processors (`preSend`, `preLLM`, `postToolCall`, `toolResponseProcessors`, …). |
| Loop shape | `turn → step → attempt`, fed by an inbox that supports steer, followup and inject. | A state machine derived from context: `llm-call-required`, `tool-response-required` or `user-input-required`. |
| Human-in-the-loop | In-process `ask` → approval service → answerers. | The turn ends with `required_actions`. The client resumes by starting a *new turn*. |
| Strength for us | Extensibility, a clean tool lifecycle, event taxonomy, event-sourced persistence. | Context engineering, large results, compaction, subagents, MCP, a crash-consistent runtime. |

## 1. DeepSeek Harness

### 1.1 Architecture

`dsh` is built on **Cordis**, a DI and plugin framework vendored at `vendor/cordis/src`. Cordis provides these primitives:

- **Service.** A class that claims a context key, for example `super(ctx, 'agents')`, which is then available as `ctx.agents`. The key's type is added through TypeScript declaration merging.
- **Dependencies.**
  - `static inject = [...]` declares hard dependencies. A plugin activates only when those services exist, so load order follows service availability, not config row order.
  - `ctx.inject([...], cb)` declares an optional or late dependency. It runs a child fiber that appears and disappears together with the service.
  - `ctx.get('x')` is a non-reactive optional read. Callers degrade when it returns `undefined`.
- **Effects.** Every registration is `ctx.effect(() => dispose)` on the current fiber. Unloading a plugin unwinds its effects in reverse order, and `ctx.on(...)` is itself an effect. No manual dispose bookkeeping is needed anywhere.
- **Event dispatch modes** (`vendor/cordis/src/events.ts`). These are part of each event's contract:

  | Mode | Behavior |
  |---|---|
  | `emit` | Synchronous, fire-and-forget |
  | `serial` | Awaited, in order |
  | `parallel` | Awaited concurrently; errors are collected into an `AggregateError` |
  | `bail` | Stops at the first value |
  | `waterfall` | Middleware. `next()` delegates to the next listener or to the built-in behavior; not calling `next()` vetoes it |

The running product is a **plugin tree built from layered YAML** (`packages/bundle/*/cordis.patch.yml`, applied in the order profile → home → `--patch`). The smallest useful tree is `packages/bundle/sdk-minimal/cordis.patch.yml`, which contains only:
- `dsh-llm`, `dsh-session`, `dsh-system-prompt`, `dsh-tools`, `dsh-agent`, `dsh-llm-retry`, `dsh-agent-loop`
- one adapter, one tool, a sandbox, and invariants

**The spine is five services, each with a single responsibility:**

| Package | Service | Owns |
|---|---|---|
| `packages/core/session` | `ctx.sessions` | Append-only `SessionEvent` log, `deriveMessages()` |
| `packages/core/system-prompt` | `ctx.systemPrompt` | Ordered prompt sections, contexts, variables, and tool-schema collection |
| `packages/core/tools` | `ctx.tools` | Scoped registry and guarded execution pipeline |
| `packages/core/agent` | `ctx.agents` | `Agent` interface, live registry, `agent/*` events, factory slot |
| `packages/llm/llm` | `ctx.llm` | Message and stream vocabulary, adapter registry |

The **loop is a separate plugin** (`packages/core/agent-loop`, `ctx.agentLoop`). It registers the one factory that `AgentRegistry.setFactory()` accepts.

The rule in `packages/README.md` is that extensions depend on *service definitions*, never on concrete providers. For example, hooks import `dsh-agent`, not `dsh-agent-loop`.

**Capability seams** (`docs/capability-seams.md`) repeat one three-role pattern:

| Role | What it is | Examples |
|---|---|---|
| Definition | An abstract `Service` with no I/O | `SpillStore`, `CompactionEngine`, `SandboxProvider`, `SessionPersistence`, `ctx.subagents` |
| Provider | A sibling package that implements it | `spill-local`, `compaction-basic`, `sandbox-local`, `session-persistence-jsonl` |
| Consumer | Usually a tool or a command | |

**Per-agent scoping** (`packages/core/scope`):
- `createScope(ctx, key)` gives every agent its own `agent.ctx`.
- Events carry a `Scoped<T>` carrier, so a listener registered on `agent.ctx` sees only that agent's events and is removed when the agent is disposed.
- Subagents restrict tools and add prompt sections through the child's `agent.ctx` (`packages/subagent/subagent/src/child-agent.ts`).

### 1.2 Execution flow (traced)

```text
apps/cli/src/bin.ts → profile-boot → packages/boot/app-boot (Cordis Loader over layered patches)
  → plugins mount (llm, session, system-prompt, tools, agent, agent-loop, adapters, tools, policies)
Host (bundle/headless/src/index.ts | sdk/server/src/server.ts):
  ctx.agents.create({sessionId, agentOptions, setup}) → AgentLoop.createAgent → ReactLoopAgent
  agent.followup(createUserMessage(...))  → inbox.splice('next-turn') → wakeDriver() → kick()
  kick(): while (await turn()) {}
    turn(): append turn/start
      loop:
        preStep(): inbox.claim → ctx.systemPrompt.assemble() → waterfall agent/pre-step (reject | enter)
        append step/start
        step(): for attempt in attempts:
          waterfall agent/request → ctx.llm.prepareCall()
          append system/message (reconciled), user/message (first attempt), request/header, request/context
          request = freeze(session.deriveMessages())
          preparedCall.stream(request) → waterfall llm/stream → LlmAdapter.stream() → StreamChunk*
            → emit agent/assistant-stream (transient frames)
          on finish{error}: append assistant/attempt → waterfall agent/request-error → retry | throw LlmError
          on success: append assistant/message; no tool calls → completed
          executeToolCalls(): tool/call → prepare (tools/pre-execute + ask + guards)
                              → dispatch (tools/execute → ToolDefinition.execute)
                              → finalize (tools/post-execute) → tool/result (in model order)
        append step/end
        if the turn is over and the next-step inbox is empty → serial agent/turn-stopping → break
      append turn/end{reason}
  host: await agent.whenIdle(); read the result from the log (turn/end reason + last assistant/message)
```

### 1.3 Important modules, classes and interfaces

**Agent** (`packages/core/agent/src/types.ts`, `runtime-types.ts`)
- `Agent` has these members:
  - identity and configuration: `id`, `options` (provider, model, reasoningEffort, maxTokens), `session`, `inbox`, `status`, `ctx`
  - lifecycle: `cancel(cause)`, `whenIdle()`
  - input: `send`, `followup` (next turn, wakes the agent), `steer` (next step, wakes the agent), `inject` (next step, does not wake it)
- There is no `run(prompt)` call. Callers enqueue input and then await `whenIdle()`.

**Loop** (`packages/core/agent-loop/src/agent.ts`, class `ReactLoopAgent`)
- Phases: `idle | maintenance | running{abort, turn, step}`.
- `step()` returns `completed | max-tokens | null`, where `null` means the tools are owed another request.

**Session** (`packages/core/session/src/index.ts`, `types.ts`)
- `Session.append(type, data, surfaceOp?)` is synchronous. It JSON-snapshots and deep-freezes the event, then fires `session/event`.
- Surface events carry `surfaceOp: 'append' | {op:'replace', startSeq, endSeq}`. This is how compaction shadows a range without deleting anything.
- `deriveMessages()` folds the surface events into model history.

**LLM** (`packages/llm/llm/src/{index,types,message,assembler,error,retry-policy}.ts`)
- `abstract class LlmAdapter`. The only required method is `stream(GenerateOptions): AsyncIterable<StreamChunk>`.
- `StreamChunk` is one of `block-start`, `text-delta`, `reasoning-delta`, `tool-call-delta`, `block-end{block}`, `usage` or `finish{reason, replayState?}`.
- `FinishReason` is one of `stop | tool-calls | max-tokens | aborted{failure} | error{failure}`. **Errors arrive inside the stream**: `LlmRuntime.adapterStream` turns an adapter's throw into a terminal `finish` chunk.

**Messages** (`packages/llm/llm/src/message.ts`)
- Roles: `system | developer | user | assistant | tool`.
- `content: ContentBlock[]`. Block types are `text`, `reasoning`, `image`, `file`, `tool-call{id,name,arguments:string}`, `tool-addition` and `tool-removal`.
- `source` records where a message came from. It can be user, model (with an opaque `replayState`), tool, system-prompt, or a kind added by a plugin.

**Tools** (`packages/core/tools/src/index.ts`, `schema.ts`, `json-schema.ts`)
- A `ToolDefinition` has:
  - `name`, `description`, `parameters` (JSON Schema)
  - `output{schema, render}`
  - `execute(args, exec)`, which returns a JSON *value*
  - optionally `timeoutMs`, `isConcurrencySafe(args)`, `projectContent` and `finalizeContent`
- `defineTool()` is the project's own schema DSL. It compiles to JSON Schema and has its own validator; it does not use zod.

**Errors** (`packages/llm/llm/src/error.ts`)
- The base class is `HarnessError(message, code)`.
- Subclasses: `LlmError(failure)`, `ToolNotFoundError` (`UNKNOWN_TOOL`), `ToolArgsError` (`INVALID_ARGS`), `ToolOutputError` (`INVALID_TOOL_OUTPUT`).
- `LlmFailure.code` values are provider-neutral: `AUTH`, `QUOTA`, `RATE_LIMIT`, `CONTEXT_WINDOW_EXCEEDED`, `INVALID_REQUEST`, `SERVER`, `TIMEOUT`, `TRANSPORT`, `EMPTY_RESPONSE`, `ABORTED`, …

### 1.4 The agent loop in detail

**Termination conditions:**
- no tool calls
- `max-tokens`, which is sticky for the rest of the turn
- a tool result with `concludesTurn`
- an `agent/pre-step` reject, which ends the turn as `blocked`
- abort (cause `user | parent | disposed | hook`)
- error

**Loop protection: there is no max-steps or max-turns cap in the loop.** Grepping `packages/core` for maxSteps, maxTurns and maxIterations finds nothing. Protection is provided by plugins instead:
- `packages/guard/repeat-tool-reminder` gives advisory reminders when the same call repeats `[3,5,8]` times, and never vetoes.
- `packages/guard/timeout-policy` is a per-tool deadline.
- There is an explicit `TODO(stop-loop-guard)` in `hooks-claude-code` about uncapped forced continuations.

**Cancellation:**
- There is one `AbortController` per run, and `signal.throwIfAborted()` is called after every await.
- A partial assistant stream is committed as `interrupted`.
- Tool calls that never started get `TOOL_ABORTED_BEFORE_DISPATCH` results.
- On a failed step, `ToolCallRecovery` (`core/session/src/repair.ts`) writes error results for any call that has none. **The transcript is always left valid.**

**Retry is a plugin**, `packages/llm/llm-retry`:
- The loop only emits the `agent/request-error` waterfall. A listener returns `{kind:'retry'}`.
- Backoff is exponential with jitter and honors `providerRetryAfterMs`.
- Defaults: `maxRetries` 5; retryable codes `EMPTY_RESPONSE`, `RATE_LIMIT`, `SERVER`, `TIMEOUT` and `TRANSPORT`.
- The retry count is stored as a session projection, so it survives a resume.

### 1.5 Tool execution lifecycle

The scheduler lives in `packages/core/agent-loop/src/tool-calls.ts`. The pipeline is documented in `docs/tool-execution-pipeline.md`, and the code matches it.

1. **Plan.** Parse the arguments. Invalid JSON is passed through as a string, so the tool's own validation reports the failure.
2. **Classify.**
   - A call is `parallel` only if `isConcurrencySafe(args) === true`; otherwise it is `exclusive`, which fails closed.
   - Parallel calls share a rolling pool of size `DEFAULT_MAX_PARALLEL_TOOL_CALLS = 10` (`constants.ts`).
   - An exclusive call acts as a barrier.
3. **Log `tool/call`**, before anything runs.
4. **`prepare`**, run serially:
   - Run the `tools/pre-execute` waterfall, which returns `allow | deny | cancel | ask`.
   - `ask` goes to `ctx.approval`. **If no approval service is mounted, the call is denied.**
   - Monotonic guards can deny but never force an allow.
   - Arguments are not rewritable at this point, on purpose, because they are already logged.
5. **`dispatch`**, the only concurrent stage:
   - The `tools/execute` waterfall wraps the body (for timeouts and metrics). Wrappers may replace only the signal.
   - A missing tool gives `UNKNOWN_TOOL`. Any throw becomes an error result.
6. **`finalize`**, in model order:
   - `projectContent`
   - the `tools/post-execute` waterfall, which returns `accept{content?, value?, additionalContexts?} | block{feedback}`
   - `finalizeContent`
   - the `tools/result` emit, which delivers a frozen result
7. **Log `tool/result`.** Any `additionalContexts` go into the next-step inbox.

**Tool errors never propagate into the loop.** They are always results that the model can see.

### 1.6 Events

There are three domains (`docs/architecture.md` and `docs/event-producer-consumer.md`; checked in source).

**Durable session events.** These are `SessionEventMap` keys, extensible through module augmentation.
- Core events: `turn/start|end`, `step/start|end`, `system|developer|user|assistant/message`, `assistant/attempt`, `tool/call`, `tool/result`, `request/header`, `request/context`.
- Added by plugins: `compaction/*`, `approval/asked|decided`, `llm/retry`, `subagent/descriptor`, `todo/write`, …
- An unknown event type without `ignorable: true` makes a reader refuse the log, which fails safe.

**Live agent events.** Each event has a fixed dispatch mode, and only waterfalls can change behavior.

| Event | Mode | Effect |
|---|---|---|
| `agent/created` | serial | A throw rolls back creation |
| `agent/pre-step` | waterfall | Reject, or rewrite the claimed messages |
| `agent/request` | waterfall | Changes the call config only, not the messages |
| `agent/request-error` | waterfall | Can request a retry |
| `agent/turn-stopping` | serial | A listener can `steer` to continue the turn |
| `agent/status`, `agent/inbox/*`, `agent/assistant-stream`, `agent/error`, `agent/disposed` | emit | Observation only |

**Capability events:**
- waterfalls: `llm/stream`, `system-prompt/assemble`, `tools/pre-execute`, `tools/execute`, `tools/post-execute`
- emits: `tools/result`, `tools/change`

**External hook bridges** (`packages/hooks/hooks-claude-code`) map Claude-Code-style shell hooks onto these same events. This shows that the event set is expressive enough for third-party hook protocols.

### 1.7 Context construction

`SystemPrompt` keeps layered registries:
- **Sections:** numeric `order`. The `SECTION_ORDERS` constants run from `HARNESS_IDENTITY` at −1000 to `DEPLOYMENT_PERSONA_SUFFIX` at 10200.
- **Contexts:** runtime state such as sandbox policy and approval policy.
- **Variables:** `{{model}}` and `{{cwd}}`. An unknown variable fails loudly.
- **Tool providers.**

**Invariant: "model-visible means logged."**
- The system prompt becomes `system/message` events.
- Runtime context becomes a synthetic `user/message` with `source.kind='runtime-context'`, appended only when it changes.
- Tool-set changes become `developer/message` `tool-addition` / `tool-removal` blocks.
- `packages/core/agent-loop/src/invariant.ts` enforces all of this at runtime: it fails if a request differs from `session.deriveMessages()`.

**Token budgeting lives outside the loop**, in `packages/llm/token-meter`. It anchors on the last real usage and adds a heuristic delta of 4 characters per token plus fixed overheads.

### 1.8 Persistence and sessions

**Storage interface.** `SessionPersistence` (`packages/session/session-persistence`) exposes `create`, `open(id, 'read'|'write')`, `flush`, `stat` and `list`. The returned handle supports `read`, `append`, `flush` and `close`.
- There is a single writer per session, protected by a lease (`session-persistence-jsonl/src/lease.ts`).
- The JSONL backend is a **listener on `session/event`**. It uses write-behind batching and drains on `session/flush` **[batch constants unverified]**.
- `session-checkpoint-policy` wraps `llm/stream` so the request prefix is durable before the model is called.

**Format.**
- Files are `session.vN.jsonl[.zstd]`.
- Generations are immutable, and each `vN → vN+1` migration is its own package.
- A torn tail is discarded on read.

**Resume, fork and replay.**
- *Resume:* replay the log into a new agent, then append `interruptedTurnClosers` (synthetic tool errors, `step/end`, and `turn/end{interrupted}`).
- *Fork:* `buildForkSeed(events, boundary)` copies a closed prefix.
- *Replay:* `ProjectionDefinition{init, apply}` is a set of pure folds (`packages/session/session-projection`) that give UI and policy state.

**Session query.** `session-query-sqlite` builds FTS5 indexes over live and persisted sessions.

### 1.9 Compaction and large results

**Compaction.**
- `CompactionEngine` (`packages/compaction/compaction`) has three methods: `compactIfNeeded(agent, 'pressure'|'context-overflow')`, `compactNow` and `compactRegion`.
- `BasicCompactionEngine` (`compaction-basic`) is triggered in two ways:
  - an `agent/pre-step` pressure check, where the threshold is `min(window·0.8, window − reserved − headroom)`;
  - `agent/request-error` with `CONTEXT_WINDOW_EXCEEDED`, which compacts and then retries, within a retry budget.
- The algorithm:
  1. Optionally run a model-free **tool-result pruner** that keeps the head and tail of old results.
  2. `selectCompactableRange` keeps a recent tail (`retainRatio 0.16`) and keeps each tool call paired with its result.
  3. Summarize using **the conversation's own prefix**, so the provider's KV cache still hits, followed by a fixed checkpoint instruction.
  4. Commit `compaction/start` → `compaction/summary` → a `user/message` with `surfaceOp: replace` → `compaction/end`.
- **Nothing is deleted.** The summarized range is only shadowed.

**Spill (large results)** has three pieces:
- `SpillStore.saveText(...) → SpillRef{locator, bytes, retrievalHint}` (`packages/spill/spill`), a one-method seam.
- `spill-policy`, a `prepend` listener on `tools/post-execute`. When a result exceeds `maxInlineTokens` (12,500 in the base bundle), it saves the full text and replaces the result with head + `[...]` + tail plus a notice giving the locator.
- Failures are best-effort: on any error, the content stays inline.

### 1.10 Subagents, MCP, safety and observability

**Subagents** (`packages/subagent/*`)
- `ctx.subagents` is a *named multi-provider registry*: `SubagentProvider{capabilities, inheritsParentContext, start(req) → SubagentRun{result: Promise<SubagentResult>}}`.
- Providers:
  - in-process *spawn*: a fresh session
  - in-process *fork*: seeded with the parent's completed-turn prefix
  - out-of-process: ACP, Codex, Claude Code, dsh-sdk
- Every child has its own session and a scoped `ctx` with restricted tools.
- `maxDepth` defaults to 1. When the parent's signal aborts, the child is cancelled.
- Background runs go through `ctx.jobs`, and completion is delivered back as `followup` or `inject`.
- The subagent tool registers only when its provider appears.

**MCP** (`packages/mcp/mcp-client`)
- One plugin per server, with a reconnecting supervisor.
- Tools are registered as ordinary `ctx.tools` entries named `mcp__<server>__<tool>`, so **every tool policy applies to them automatically**.
- `listChanged` triggers a re-sync, which swaps tools in two phases.
- Server instructions become a prompt section.

**Safety**
- `SandboxProvider.confine(argv, policy) → ConfinedArgv` only wraps argv and **fails closed** with `SandboxUnavailableError`. Runners: bwrap/Landlock, Seatbelt, Windows ACL.
- Approval is `tools/pre-execute → ask → ApprovalService`. It records `approval/asked|decided`, dispatches the `approval/request` waterfall to answerers, and fails closed when nobody answers.
- Permission presets map onto a sandbox mode plus an approval policy.

**Observability**
- `session-telemetry` produces one record per session event. The `session-telemetry/record` waterfall is the redaction point.
- `session-telemetry-otel` exports OpenTelemetry *logs*. No tracing spans were found.
- `runtime-diagnostics/invariants` holds runtime contract checks.

### 1.11 Strengths

- **A small core in practice.** The loop, registry, prompt, log and LLM are five separate seams. Retry, compaction, spill, approvals, persistence and telemetry are all plugins.
- **Precise extension semantics.** The dispatch mode says exactly whether a listener can veto, rewrite or only observe. The waterfall "call `next()`, then fold in your change" idiom lets policies compose.
- **Event sourcing.** Resume, fork, replay, persistence, telemetry and search all fall out of one log. The invariant makes debugging "what did the model actually see?" trivial.
- **A deterministic tool pipeline.** Policy stages are serial, bodies run concurrently, and results commit in model order. Concurrency is opt-in per call.
- **Transcripts that are always valid.** Synthetic results are written for aborted or failed calls.

### 1.12 Tradeoffs

- **Cognitive cost.** Behavior is spread across many listeners, and you need the event catalog to know what happens. The code relies on long defensive-contract comments to compensate.
- **The invariant is expensive.** Every model-visible input must become an event, and plugins that change content must register pure projections.
- **No step cap in the core.** Runaway loops are bounded only by optional plugins.
- **Machinery sized for a product.** Hot reload, layered YAML, i18n and generation-migration packages are not justified for a small library.
- **Cordis has no Python equivalent**, and replicating it would dominate the codebase.

## 2. TrueForge

### 2.1 Architecture

**Dependency direction:** `packages/trueforge` (the server) → `packages/trueforge-core` (the library). The SDKs and UI packages are clients.

**`packages/trueforge-core`** (~17k lines of TS) is the harness itself. It has no HTTP and no database code.
- `src/core/runtime/`
  - `AgentThread.ts`: the loop
  - `AgentThreadOrchestrator.ts`: multi-thread scheduling
  - `DeferredTool.ts`, `OpenToolCallCloser.ts`
- `src/core/llm/`: `ILLM` and `VercelAILLM`. The Vercel AI SDK is used **only as a single-step provider adapter**; its loop and tool execution are not used.
- `src/core/mcp/`: tools are **MCP-shaped everywhere**. Includes `IToolSet`, `ToolSet`, `LocalToolMCP`, `RemoteMCP` and `executeToolCalls`.
- `src/core/capabilities/`: the `AgentCapability` plugin unit, plus builtins for compaction, large responses, subagents, ask-user, web search and datetime.
- `src/core/sandbox/`: the sandbox tool, Code Mode, and the Daytona and TFY providers.
- `src/agent-session/`: `Sessions`, `SessionHandle`, `TurnHandle`, `ISessionStore` and `TurnResourceResolver`.

**`packages/trueforge`** is the Hono/OpenAPI server.
- Kysely stores for SQLite (standalone mode) and Postgres.
- In hosted mode, Redis is used only for resumable streams and for request-reply between replicas.
- **There is no job queue.** A turn runs as an async generator inside the replica that received the request.

**`AgentSpec`** (`agent-session/schemas/agentSpec.ts`) is the authored configuration. The resolver turns it into an `AgentDefinition{modelClient, instruction, messages, toolSets, iterationLimit, responseFormat, …}`, and `builtinsFromSpec` turns the spec's flags into capabilities.

### 2.2 Execution flow (traced)

```text
src/cli.ts → src/main.ts (STANDALONE: SQLite | Postgres+Redis)
HTTP POST turn → apis/turns.ts beginTurnExecution
  AbortController + SERVER_EXECUTION_TIMEOUT_SECONDS (600 s) + activeTurns.track()
  SessionHandle.createTurn():
    resolve previous turn (tip | none | fork id) → freeze a still-running previous turn
    resolver: spec → sandbox handle (lazy) → AgentDefinition per thread → configureCodeMode
    rebuild AgentThreads from the previous turn's per-thread snapshot
    orchestrator.send(input)        ← validate + append (send-before-commit)
    store.createTurn(...)           ← one atomic commit
  TurnHandle.stream():
    for event in orchestrator.execute(signal):
      persistExecutionEvent(event)  ← store first
      yield event                   ← then SSE / EventSubscription (Redis Streams | memory)
    finally: terminal state (done | error | cancelled) — first terminal write wins
AgentThread.execute():
  preSend processors → init tools (listTools in parallel; auth-required → exit)
  for (;;) switch deriveAgentThreadState(context):
    llm-call-required      → iteration cap → stepLLMCall
        preLLM processors (compaction) → transformToLLMRequest → modelClient.create() (stream)
        enrich tool calls with tool_info → appendToContext
        finish_reason=length → error; no tool calls → AGENT_DONE
    tool-response-required → stepToolResponse
        executeToolCalls (Promise.all) → ToolResponseProcessors (offload) → appendToContext
        postToolCall processors; subagent sentinel → AGENT_CREATE_SUBAGENT → exit
    user-input-required    → emit TOOL_APPROVAL_REQUIRED / TOOL_RESPONSE_REQUIRED → exit
```

### 2.3 Important modules, classes and interfaces

**LLM** (`core/llm/ILLM.ts`)
- `ILLM.create(body): AsyncGenerator<Chunk, RawAssistantMessageWithUsage>`. The generator's *return value* is the assembled message.
- The internal lingua franca is the **OpenAI Chat Completions shape**.
- Internal messages add `thinking_blocks` (kept for replay), `reasoning_content` (for display; stripped from context) and `source`.

**Tools** (`core/mcp/IMCPServer.ts`)
- `IToolSet{listTools, callTool(params, approvalDecision?), toolCallInfo}`.
- `CallToolResponse` is a **discriminated union of control-flow outcomes**: `{result} | {authRequired} | {createSubAgent} | {approvalRequired} | {clientSideToolRequired}`.
- Local tools use `defineTool({name, description, schema: zod, handler})`. Validation failures come back to the model as a result; they are never thrown.
- **Source and policy are split:**
  - `RemoteMCP` (a `ToolSource`) owns the connection and cache.
  - `ToolSet` applies a per-agent `ToolSelectorPolicy`: enable, disable, preload and require-approval.

**Capability** (`core/capabilities/AgentCapability.ts`)

```ts
interface AgentCapability {
  systemToolSets?; preSendProcessors?; preLLMProcessors?; preLLMEphemeralProcessors?;
  postToolCallProcessors?; toolResponseProcessors?; instructionBuilders?;
  state?: { key; load(state) };   // cross-turn KV
}
```

Processors are async iterables that yield `append | overwrite | passthrough | capability-state` outputs.

**Errors** (`core/errors.ts`): `AgentHarnessError(code)` and `McpConnectionError(statusCode)`. The server maps these to HTTP 400, 404 or 422.

### 2.4 The agent loop in detail

**State is derived from the context, not stored.** `deriveAgentThreadState` looks at the tool calls on the last assistant message that have no result, and at their `tool_info` flags. `VALID_TRANSITIONS` guards against illegal jumps.
- **Consequence:** a thread rebuilt from its persisted context resumes at the correct step, with no stored state-machine variable.

**Persist before mutate** (`core/runtime/AGENTS.md`):

```ts
yield event;      // consumer persists; may throw
mutateMemory();   // only after persistence succeeded
```

Memory can never get ahead of the database.

**Termination:**
- no tool calls
- `finish_reason: 'length'`, treated as an error
- `iterationLimit`: code fallback `DEFAULT_ITERATION_LIMIT = 25` (`AgentThread.ts:100`); spec default 100, maximum 1024
- abort
- user input required
- auth required

**`execute()` never throws.** A top-level catch turns any throw into `AGENT_DONE{status:'error'}`.

**What is missing:**
- **No LLM retry.** `buildStreamTextArgs` hard-codes `maxRetries: 0` (`VercelAILLM.ts:953`).
- No detection of repeated tool calls.
- No per-tool timeout beyond the MCP transport timeouts.
- No cap on parallel tool calls.

**Transcript hygiene:** `OpenToolCallCloser`, a `preSend` processor, fills in dangling tool calls with an error result.

### 2.5 Context engineering

**Assembly per step** (`AgentThread.transformToLLMRequest`):
1. The system prompt, built once through `InstructionBuilder` as nested XML sections: identity, internal rules, sandbox, deferred tools, capability sections, and user instructions (root only).
2. The seed messages.
3. The persisted context, with filtered rows removed and `tool_info` stripped.
4. The `preLLMEphemeral` transforms, which are **not persisted**.
5. `response_format`, parameters and tools.

Harness-injected text is sent as a `user` message wrapped in `<tfy-internal>`.

**Token estimate:** chars/4, corrected by the real `usage.input_tokens` after each call. `computeAssistantMessageUsage` attributes tokens by category: harness, skills, instructions, tool definitions and messages.

**Deferred tool loading** (`DeferredTool.ts`):
- Only each server's name and description go into the prompt.
- The model uses four meta-tools: `list_tools`, `get_tool_info`, `get_tool_output_schema` and `call_tool`.
- `call_tool` goes through the real `ToolSet`, so approval still applies.

**Code Mode:**
- The model writes Python inside the sandbox that calls MCP tools through `mcp_client.py`.
- Those calls are bridged back to the host over NATS or UDS and pass through the same `IToolSet.callTool`.
- **Credentials never enter the sandbox.**
- Approval-gated and interactive tools are rejected in Code Mode.

### 2.6 Large tool results

`LargeToolResponseProcessor` (`capabilities/builtins/LargeToolResponse.ts`) uses two thresholds, a **per-call** threshold of 6,000 tokens and a **per-step total** of 10,000 tokens:
- Every result over the per-call threshold is blocked.
- Then, while the step total is still over its threshold, the remaining results are blocked **largest first**.

What a blocked result becomes depends on its category:
- **Failure:** truncated to 500 characters.
- **Sandbox output:** a "write it to a file" hint plus a 100/100-character head and tail preview.
- **MCP result:** if a sandbox exists, the full result goes to `sandbox.writeArtifact(...)` and the model is told the path and how to grep or parse it. **Without a sandbox, only the preview survives.**

**Observed bug:** `AgentSpec` exposes the three thresholds, but `builtinsFromSpec.ts:58` calls `largeToolResponse({dynamicSubAgentsPresent, logger})` without them, so the defaults always apply.

### 2.7 Compaction

`ContextCompaction` (`capabilities/builtins/ContextCompaction.ts`) is a `preLLM` processor that is checked before **every** LLM call.

- **Trigger:** `usage + prompt ≥ threshold`, where the threshold is an explicit value, else `0.8 × contextLength` (capped at `contextLength − max_tokens`), else 50k.
- **Algorithm:**
  1. Flatten the entire context into one indexed transcript string.
  2. Make one non-streaming call to the same model with an 8-section summary prompt: intent, concepts, files, errors, problem solving, user messages, pending tasks, next step.
  3. Replace the context with `[assistant: summary, internal: "do not repeat work"]` using `AGENT_CONTEXT_OVERWRITE`.
- **What is preserved:**
  - the system prompt and seed messages, because they are rebuilt on every request;
  - capability state;
  - sandbox files, so offloaded results survive.
- **No recent messages are kept verbatim.** There is no chunked summarization, so a summary call that itself overflows is unhandled **[inferred]**.
- Old turns are untouched, because the context is a copy-on-write array of ids.

### 2.8 Subagents and parallelism

**Subagents** are built from a tool plus orchestrator interception.
- `create_sub_agent` (`DynamicSubAgents.ts`) returns a **sentinel** `{createSubAgent}` rather than running anything.
- The parent's step exits and leaves the call open. The orchestrator creates the child thread.
- **Isolation:**
  - The child starts with an empty context holding only the task message.
  - It gets a `SUB_AGENT_IDENTITY` prompt and no user instructions.
  - It gets no ask-user or subagent builtins, so the **depth is fixed at 1**.
  - It *shares* the parent's tool sets, MCP connections and sandbox.
- **Result propagation:** the parent sees only the child's final text, delivered as the result of its open tool call. The full child transcript is persisted and streamed, tagged with `thread_id`.
- **Crash-safe delivery:** the completion is persisted with the child's final append, and `preComputedCompletion` replays it on resume.

**Scheduling:**
- Only leaf threads run, in **chunks** of `MAX_PARALLEL_SUB_AGENTS = 5` (`AgentThreadOrchestrator.ts:37`), merged with `Promise.race`. This is a chunked scheme, not a sliding pool.
- A parent is implicitly blocked until all its children finish.
- There is no timeout per subagent; one turn-wide abort signal covers everything.

**Tool calls:** all calls in one message run under `Promise.all`, with per-call try/catch, so failures are isolated. Approval is **batch-gated**: if any call needs approval, *none* of the calls in that message run until all of them are resolved.

### 2.9 MCP, safety, streaming, persistence and observability

**MCP** (`core/mcp/remoteMcpClient.ts`, `RemoteMCP.ts`, `convertMCPServers.ts`)
- Uses the official SDK, probing streamable-http first and falling back to SSE.
- Every request has a timeout.
- Fetch is wrapped with an SSRF guard and a 50 MB response cap.
- Reconnects and retries once when the session expires.
- Tool names are sanitized to `[a-zA-Z0-9_-]{≤64}` and de-duplicated. Harness tools claim names first.
- Header auth, or OAuth 2.1 with DCR and PKCE on the server side. An auth-required response ends the turn with a required action.

**Safety**
- Approval defaults come from MCP annotations: `require_approval_for_tools` defaults to `['@write','@destructive']`.
- There are allow and deny selectors.
- Local tools are never approval-gated.
- Code Mode enforces `blockDestructiveToolsInCodeMode`.
- The sandbox (`core/sandbox/provider/Provider.ts`, `SandboxProvider`) is provisioned **lazily**, on first use, and reattached across turns.
- **Gap:** git credentials live inside the sandbox.
- `allow_session` approvals exist in the schema but are not enforced.

**Human-in-the-loop**
- The turn ends as `done` with `required_actions`.
- The client resumes by creating a new turn whose input contains the approval or answer messages.
- Because all state is already durable, the resume can happen on any replica at any later time.

**Streaming**
- A custom JSON event protocol over SSE, not the AI SDK UI stream.
- Token deltas (`model.message.delta`) are **streamed but never persisted**. Durable content is the full `model.message`.
- Resumable SSE uses `Last-Event-ID` against Redis Streams or a memory log.
- Execution is decoupled from the HTTP response.

**Persistence** (`ISessionStore`, with a shared contract test suite of about 3.4k lines)
- Tables: `session`, `turn` (a tree through `previous_turn_id`), `turn_thread` (`context_ids bigint[]`), `thread_context_log` (immutable message bodies), `session_event` (keyed by ULID) and `thread_capability_state`.
- Copy-on-write id arrays make fork and restore cheap.
- Resume works by rebuilding threads from the snapshot, *not* by replaying events. The event log is for UI and audit.

**Observability**
- `AgentTracing` is an abstraction with spans for the root, subagents, init, local tools and MCP tools. The OSS build wires in `NOOP_AGENT_TRACING`.
- OTel is used for `traceparent` propagation only.
- `AgentThreadMetrics` tracks tokens (including cache and reasoning tokens), iterations, tool calls, subagents and summarizations.
- Cost comes only from provider-reported values; there is no price table.

### 2.10 Strengths

- **Durability is designed in, not added on.** Persist-before-mutate, send-before-commit, first terminal write wins, and cross-replica cancel.
- **Resumable by construction.** A state derived from context plus per-thread snapshots means any pause (approval, client tool, OAuth, crash between turns) is just "start the next turn".
- **Control flow as data.** The `CallToolResponse` union lets tools cause pauses and subagent spawns without special cases in the loop.
- **Serious context engineering.** Deferred tools, Code Mode, two-threshold offloading, token attribution by category, and subagents presented as a context-hygiene tool.
- **Separating tool source from policy** lets one connection serve many agents, each with its own policy.

### 2.11 Tradeoffs

- **The core is not small.** The loop knows about approval, client-side tools, auth, subagents and deferred tools through `tool_info` flags. Adding a new kind of pause means editing the state machine.
- **OpenAI message shape as the internal type.** Pragmatic, but provider concepts leak inward (for example `thinking_blocks` and `provider_specific_fields`).
- **Reliability gaps:** no LLM retry, no repeated-call detection, no per-tool timeouts, and no concurrency cap on parallel tools.
- **Blunt compaction:** it replaces everything and keeps no verbatim tail.
- **Large-result handling depends on a sandbox.** Without one, data is lost.
- **Fixed limits:** subagent depth is fixed at 1, and parallelism uses chunks rather than a pool.

## 3. Cross-framework comparison

Each row explains *why* each design exists and what it trades away.

### 3.1 Architecture

- **DeepSeek** uses a DI container with a plugin tree, because it is a *product platform*: the same kernel ships as Web, Desktop, ACP, SDK and headless, and third parties install plugins at runtime. The price is indirection.
- **TrueForge** uses a library plus a server with capabilities, because it is a *hosted service*: tenancy, HTTP, replicas. Its extension surface is narrower (capabilities, tool sources, resolver) but easier to read.
- **Lesson:** a Python library needs DeepSeek's *seams* (interfaces with clear roles), but not its *container*. Constructor injection and protocols give the same replaceability at a fraction of the cost.

### 3.2 Runtime

- **DeepSeek:** a long-lived `Agent` with an inbox, driven by `followup`/`steer`/`inject`. Built for interactive clients that interleave input while the agent is running.
- **TrueForge:** one generator per turn, with a durable snapshot per turn. Built for request/response over HTTP.
- **Lesson:** start with `runtime.run(agent, input) → Result` as a single execution, which is the simplest contract. Keep state serializable so the TrueForge-style "resume with new input" works later, and leave a hook where next-step injection can be added.

### 3.3 Agent loop

- **DeepSeek:** `turn → step → attempt`, with extension through waterfalls and no step cap.
- **TrueForge:** a state machine derived from context, with an iteration cap, and pause states built into the loop.
- **Lesson:** adopt the *derived state* idea (pending tool calls computed from the transcript) and a hard `max_steps`. Keep pauses out of the loop body: they should be outcomes returned by the tool pipeline, which the loop maps to a terminal status.

### 3.4 Tools

- **Both** turn every tool failure into a model-visible result, and neither lets an exception reach the loop. Adopt this.
- **DeepSeek** has a richer lifecycle (pre → guards → around → post, with typed decisions) and opt-in concurrency with commits in model order.
- **TrueForge** has a better *outcome* model (a discriminated `CallToolResponse`) and a better *source/policy* split.
- **Lesson:** use DeepSeek's pipeline stages, TrueForge's typed outcomes, and Pydantic in place of both schema systems.

### 3.5 LLM abstraction

- **DeepSeek** defines its own neutral vocabulary (content blocks, a stream-chunk union, in-band errors with neutral codes). This keeps the core provider-independent.
- **TrueForge** uses the OpenAI shape internally. That is fast to build, but provider details leak inward.
- **Lesson:** use DeepSeek's approach. Define a neutral `Message`/`Part` model and a `FinishReason` enum, keep provider translation in adapters, and use neutral error codes.

### 3.6 Context

- **DeepSeek** assembles ordered sections plus contexts and logs everything that is model-visible. That is excellent for audit and caching, and costly to maintain.
- **TrueForge** builds an XML sectioned prompt, uses ephemeral transforms that are not persisted, and attributes tokens by category.
- **Lesson:** have a `ContextManager` that produces an `LLMRequest` from `AgentState`, with prompt sections that have a numeric order (both repos converged on this). Keep persisted history immutable, and make reductions a *view*.

### 3.7 Events

- **DeepSeek** separates *durable facts* (the log), *live interception* (waterfalls) and *observation* (emits). This is the clearest model of the two.
- **TrueForge** has one wire-event schema that also carries persistence commands (`AGENT_CONTEXT_APPEND`, and so on).
- **Lesson:** keep observation (the event bus and observers) separate from interception (hooks and middleware). An observer must never be able to change behavior.

### 3.8 Persistence

- **DeepSeek** is event-sourced (the log is the truth). Replay, fork and search come for free.
- **TrueForge** stores snapshots plus a copy-on-write id array (the context is the truth) and keeps the events for the UI. Resume is O(1) and needs no replay.
- **Lesson:** make the in-memory `AgentState` the truth during a run. Persistence is an optional store fed by events and by checkpoints at step boundaries. Replay (Phase 15) can then work either way.

### 3.9 Compaction

- **DeepSeek:** prune first, then summarize a *region*, keep a recent tail, preserve tool pairing, and shadow rather than delete. It triggers on pressure and on an overflow error.
- **TrueForge:** replace the whole context on a threshold check before every call.
- **Lesson:** DeepSeek's algorithm is better (the retained tail, pairing, and cheap pruning first). TrueForge's integration point is simpler (a single "before LLM" hook). Combine the two.

### 3.10 Subagents

- **DeepSeek:** a provider registry, where each child is a full agent with its own log, and background jobs are supported. Maximally flexible.
- **TrueForge:** a sentinel returned by a tool, with the orchestrator creating a child thread. Resumable and parallel, but depth is fixed at 1 and only text is returned.
- **Lesson:** a subagent should be a *tool that runs a child execution through the same runtime*, with isolated state, a depth limit, a timeout and cancellation linked to the parent. That needs no change to the loop.

### 3.11 Observability

- **DeepSeek:** telemetry derived from the log, a redaction waterfall, and OTel logs.
- **TrueForge:** a tracing interface (spans) plus metrics objects.
- **Lesson:** use an `Observer` protocol over events, with a built-in metrics observer and an OTel adapter as an optional extra.

### 3.12 Safety

- **DeepSeek:** fail closed everywhere (no approval service means deny; no sandbox means refuse). Guards can only deny.
- **TrueForge:** approval defaults from MCP annotations, and credential isolation for sandboxed code.
- **Lesson:** use a policy hook in the tool pipeline that can only deny, an approval callback that fails closed, and tool classification through tool metadata.

### 3.13 Extensibility

- **DeepSeek** is the most extensible possible design, at the cost of complexity.
- **TrueForge** offers a moderate `AgentCapability` bundle, which is easy to understand.
- **Lesson:** a small set of named hook points with explicit semantics (DeepSeek), grouped into installable bundles (TrueForge `AgentCapability`) as "plugins".
